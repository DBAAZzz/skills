# 自解释代码与注释纪律

## 核心原则

**不要让人记住机器本来可以记住的事情。**

代码能表达的，不要让注释再说一遍。

规则能让机器记住，就不要让人靠自觉遵守。

代码表达不了、但未来维护者可能因为不知道而改错的重要背景，才值得写进注释。

信息的分流原则：
- **代码**表达具体行为与流程。
- **类型 / API / 状态**表达结构与使用限制。
- **运行时检查**在边界把非法输入卡死。
- **测试**表达必须长期成立的行为契约。
- **注释**表达原因、外部现实与那些机器无法保存的关键知识。

---

## 遇到注释，按 5 个问题判断

### 1. 是不是在重复代码？
例如：
```ts
// Check whether the user is logged in
if (user.isLoggedIn) {
}
```
→ **删除**。不要把代码翻译成自然语言。

---

### 2. 是不是因为代码本身不清楚？
例如：
```ts
// Calculate the user's final price after discount
const x = price * (1 - discount)
```
→ **改命名、拆函数或重构结构**，优先让代码变清楚：
```ts
const finalPrice = calculateDiscountedPrice(price, discount)
```

---

### 3. 是不是在描述一个应该被代码保证的规则？
例如：
```ts
// Must call init() before calling query()
```
不要马上接受这个注释。优先看看能不能从结构上让调用方根本无法犯错：
```ts
// 改造前：允许拿到未初始化的实例，靠注释警告调用方
const db = new Database()
db.init()
db.query()

// 改造后：未初始化前根本拿不到实例
const db = await Database.connect()
db.query()
```
同理，状态之间的互斥关系也可以交给状态建模，而不是靠注释提醒：
```ts
// 改造前：靠注释警告 status 与 data 的关系
interface State {
  status: string
  data?: User
}

// 改造后：非法组合在类型上无法表示
type State =
  | { status: "loading" }
  | { status: "success"; data: User }
  | { status: "error"; error: Error }
```
*注：选择最简单、最合适的表达方式，不要为了“绝对类型安全”无限堆砌极其复杂的类型。*

---

### 4. 没有强类型系统时怎么办？
**语言没有类型系统，不代表约束可以退化成注释；至少把约束变成可执行的失败。**

没有强类型支持时，优先在边界处进行运行时校验，并在不满足条件时明确失败（抛出异常、返回错误或退出非零状态）。可以使用断言，但不要依赖可能被优化关闭或移除的断言（如某些环境下的 `assert`）来承担生产约束。

例如：
```js
// JavaScript：入口立即抛错
function createOrder(amount) {
  if (!Number.isFinite(amount) || amount <= 0) {
    throw new Error("amount must be greater than 0")
  }
}
```
```python
# Python：明确抛出 ValueError，不依赖 assert
def create_order(amount: float):
    if not math.isfinite(amount) or amount <= 0:
        raise ValueError("amount must be greater than 0")
```
```bash
# Shell：条件不符直接退出
[[ "$amount" =~ ^[1-9][0-9]*$ ]] || {
  echo "amount must be greater than 0" >&2
  exit 1
}
```
约束仍然是机器在执行，而不是靠人脑记忆。

---

### 5. 如果代码无法表达，删除注释后未来会不会容易误改？
如果一个完全看懂代码的人，可能因为不知道背景而做出“看似合理、实际上导致事故”的修改，这条注释就**必须保留**。

常见需保留的高价值背景：
- **外部平台 / 第三方库的怪异行为**：
  ```ts
  // Safari 16.0~16.3 在页面切后台时会重复触发 visibilitychange 事件，需在此去重防二次提交
  ```
- **向后兼容**：
  ```ts
  // 这个字段虽然已废弃，但旧版 App 仍会读取，暂不可删除
  ```
- **反直觉的性能与资源取舍**：
  ```ts
  // 这里故意不创建临时数组，否则该高频热点会引发频繁 GC
  ```
- **安全与时序陷阱**：
  ```ts
  // 这里必须使用恒定时间比较，防止时序攻击泄露哈希长度
  ```
- **业务或法务强约束**：
  ```ts
  // 金额为 0 也必须写入流水表，财务对账系统要求每笔调用必须有唯一凭据
  ```

## 一条注释的最终判断标准

> **删除这条注释之后，一个已经完全看懂代码的人，会不会因为不知道这个背景，而做出一个看起来合理、实际上错误的修改？**

- **不会** → 删除注释。
- **会** → 保留注释并打磨表达。
- **本可通过代码解决** → 不要写注释，改代码（改命名 / 提函数 / 收紧类型 / 补充运行时拦截 / 加测试）。

---

## 审查代码与输出规范

审查注释时，只做四种纯粹的判断：

1. **重复代码** → 删除注释
2. **代码不清楚** → 改命名 / 拆函数 / 改结构
3. **规则未代码化** → 改类型 / API 结构 / 状态设计 / 运行时拦截 / 补充测试
4. **需保留的背景** → 保留注释并打磨

### 审查输出格式

对每一处需要处理的注释，按以下格式简洁输出：

```text
注释：
"// 原注释内容"

判断：
[重复代码 / 代码不清楚 / 规则未代码化 / 需保留的背景]

建议：
[删除注释 / 保留注释并打磨 / 改进代码]

改后代码：
// 展示改进后的代码或保留的注释
```

**输出约束**：
- 「改后代码」仅在代码结构、类型或注释文案**实际需要调整**时提供。
- 若判断为仅需删除注释，直接指出删除即可，**严禁为了凑齐格式而重复粘贴毫无变化的整段业务代码**。
- 若判断为需保留的背景，直接展示打磨后的注释，**严禁为了“改后代码”四个字强行重构无辜代码**。
