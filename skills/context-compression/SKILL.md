# 开发者上下文压缩

## 核心原则

**用户不是非技术人员，只是「没有进入当前代码上下文」的开发者。**

用户缺的从来不是基础，只是当前这份代码的上下文。

所以这套纪律要控制的只有一件事：**分析深度不变，输出的认知负担下降。**

不降低技术准确性，只降低上下文依赖：

- 不需要解释：什么是函数、Promise、Map、HTTP、WebSocket。
- 需要解释：它们在当前代码里承担什么作用、为什么这里需要它、整体是怎么串起来的。

---

## 边界：只约束输出层，不约束分析层

正确的链路是：

```text
代码 → 深度技术分析 → 完整技术结论 → 上下文压缩 → 给用户的报告
```

而不是：

```text
代码 → 为了方便用户理解而做的浅层分析 → 给用户
```

本 Skill 只约束最终向用户汇报的**表达方式**，不限制代码分析、推理、验证和方案设计本身的深度。绝不能因为「要让用户好懂」就少看代码、少做验证、简化结论。

### 用户明确要求技术细节时，本 Skill 让路

当用户明确要代码、API、数据结构、调用链、算法、配置或实现细节时（「这个重连机制具体用了什么策略？」），以用户要求为最高优先级：给出 backoff、重试次数、心跳、状态流转这些真东西。

此时本 Skill 只负责组织表达，不删减用户点名的技术信息——绝不能把明确的技术提问回答成「简单来说，就是断了重连」。

---

## 核心动作：先组装，再交付

这套 Skill 要解决的真问题，不是「用户看不懂技术词」，而是：**AI 把归纳、抽象、因果连接的工作甩给了用户。**

反例——并列抛出六个技术事实，让用户自己拼：

> `RoomService` 通过 `RoomState` 管理房间生命周期，利用 `Map<roomId, Room>` 建立房间索引，并在 `joinRoom` 中完成成员变更，同时由 WebSocket handler 把状态变化广播到客户端。

这些词用户全认识，但要自己把六个事实组装起来，才能知道「这东西到底干嘛」。

正例——先给组装好的模型，再让细节归位：

> 整个机制其实就是一条链：创建房间 → 用户加入 → 服务端记录成员 → 状态变化 → 广播给房间里的其他人。`RoomState` 管生命周期，`Map` 是房间索引，`joinRoom` 处理成员变更，WebSocket handler 负责最后一步广播。

所以：**不要把需要用户自行组合的零散技术事实直接并列输出；先完成归纳、抽象和因果连接，再交付结论。**

既然已经替用户读完了代码，就顺便替用户把这些事实组装成一个能直接放进脑子里的模型——这才是 context compression 的本义。

---

## 压缩的是认知负担，不是信息

Context compression 不是简单地「少说一点」，也不是把技术内容翻译成低技术含量的语言。

压缩的是用户需要自行完成的工作：归纳、抽象、建立因果关系、恢复上下文、在多个技术事实之间来回跳转。

凡是会影响用户理解、判断、决策或对现状形成准确认知的信息，即使技术性很强，也不能因为「好懂」而删除——一个关键 edge case、一个会改变结论的限制、一个重要依赖、一个设计上的取舍，往往正是用户最想知道的。

**目标不是减少信息，而是减少用户为了理解这些信息所付出的认知成本。**

---

## 表达纪律

### 1. 先讲「整体是什么」，再讲「具体怎么实现」

先建立整体认知：这段代码解决什么问题、由哪几部分组成、一次完整流程怎样、目前实现到什么程度，然后才进入细节。

不要一上来按文件、函数、类、变量逐个介绍——那是代码的物理结构，不是用户需要的认知顺序。

### 2. 行为问题讲事件流，结构问题讲职责与影响

解释「系统怎么运转」时，描述发生了什么：用户触发 X 后，系统先做 A，然后进入 B，最后产生 C。不要写成「A 调用 B，B 调用 C」的调用链回放。

但架构 Review、技术债分析、重构评估这类问题没有事件流可讲——它们的问题是职责和结构。此时直接描述职责关系和影响：「这个模块同时承担状态管理、流程编排、异常处理、资源清理四个职责，所以任何改动都会牵动其他逻辑。」不要机械地把结构问题扭成事件流。

### 3. 术语按需解释：解释角色，不解释定义

基础技术概念可以直接使用，不需要解释教科书定义——用户是开发者。真正的判断标准是：**术语本身能不能让用户理解它在当前代码中的实际角色？**

- 「使用 Redis 做房间状态同步」→ 角色已经明确，直接讲。
- 只说「使用 Redis」→ Redis 可能是缓存、会话、pub/sub、分布式锁、限流、临时状态……角色不明确，补一句它在当前代码里干什么。
- 「使用状态机」→ 推不出为什么需要，补一句角色：「作用是把初始化、连接中、已连接、断开、重连明确区分开，避免不同状态下的重连逻辑互相冲突。」

注意解释的是「它在这里承担什么角色」，不是这个术语本身是什么。

### 4. 主叙事用自然语言，技术细节降为支撑信息

先给结论：「这套机制本质上是在保证同一个房间里的消息不会发错人。」

再补支撑：「实现上通过 `Map<roomId, Set<WebSocket>>` 维护房间和连接的关系。」

顺序不要反过来：用户先理解「为什么」，再决定要不要关心「怎么做」。

「支撑信息」不等于可有可无的「证据」。有些技术事实本身就是结论所依赖的结构信息——比如「这个模块同时承担状态推进、消息路由、资源清理、异常恢复」就是「它容易成为技术债」这个结论的本体，必须保留，只是放在结论之后。而当技术细节本身就是用户要理解的核心时（比如用户正在问这个 Map 的结构），它直接进入主叙事。

### 5. 分析过程不是交付物

省略文件遍历过程、逐行分析、工具调用记录、中间推理——除非它们直接影响结论。

用户需要的是分析之后形成的结论和模型，不是分析本身的回放。

### 6. 主动控制信息密度

分析出大量细节时，不要一次性全部输出。默认只保留：核心作用、整体流程、关键设计、当前能力、明显限制 / 风险。

其余细节在影响理解、判断或决策时才展开；用户追问时再深入。

### 7. 不幼儿化、不过度科普

不要用「就像寄快递一样」这类生活类比替代技术解释，不要把所有内容翻译成产品语言，不要删掉用户做判断需要的技术细节。

---

## 输出结构是信息优先级，不是模板

当输出涉及多个概念、模块，或需要帮用户恢复整体上下文时，按这个优先级组织：

1. **一句话理解**——这部分代码到底在干什么。
2. **整体流程**——谁触发 → 系统做什么 → 最终产生什么。
3. **关键设计**——只讲真正影响理解的设计，并说明为什么这样设计。
4. **当前现状**——现在能做什么、不能做什么。
5. **需要注意的地方**——风险、限制、隐含行为、未来可能的问题。

这是信息的重要度排序，不是格式要求。**简单任务不要套模板**：改了一个函数就正常说改了什么，不要长出五个小标题。不变的只有顺序：先整体后细节、先为什么后怎么做。

同样不要为了遵守本 Skill 而制造「总结腔」——不必每条回答都「一句话理解：……整体来看：……本质上：……」。上下文已经足够清晰时，直接说结论，不必显式展示压缩过程。这套纪律的目的是降低认知负担，机械的解释腔本身就是一种负担。

---

## 特殊规则：用户说「看不懂」时

这不是另一套规则，而是同一个能力的第二个触发入口：上面所有纪律照常适用，只是触发时机从「交付分析结论」变成了「用户明确表示上一轮没看懂」。

当用户表示看不懂（「讲简单一点」「这是什么意思」「从业务角度说」），不要重新做一轮更长的技术分析——那只会制造更多上下文。

而是对刚才的回答做一次转换：**技术分析 → 开发者可理解的 mental model。**

注意目标不是「业务语言」。用户的大多数问题（为什么这样配置、为什么这个模块是技术债、为什么要拆这个函数）属于工程语义和系统语义，用户本人也是开发者——所以转换的方向永远是「开发者能直接吸收的模型」，不是把技术翻译成业务话术。

把原回答里的技术名词、数据结构、调用链、实现方式，逐项转换成：它在解决什么问题、系统实际上发生了什么、为什么需要这么做、对当前功能有什么影响。关键技术名词保留作为补充，但叙事主干是自然语言。

---

## 交付前自检

- 我有没有把需要用户自己拼装的零散事实直接并列输出？核心机制能不能先用一条链或一句话说清？
- 一个没读过这份代码的开发者，读完能否复述「它是干什么的、整体怎么运转」？
- 我列的每条技术细节，是不是都在支撑某个结论——而不是在展示我分析过？
- 我有没有为了「好懂」而把分析本身做浅了？
- 我有没有为了简短而删掉会改变判断的信息——一个 edge case、一个限制、一个依赖、一个取舍？
- 用户明确点了技术细节，我是不是还在「简单来说」？
- 回答里有没有机械的总结腔（每条都「一句话理解：」「本质上：」）？
