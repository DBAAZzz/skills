# Code Ablation & Minimalist Refactoring（代码消融与极简重构）

生成代码容易引入假想扩展点、重复防御和紧耦合实现细节的测试。代码消融以奥卡姆剃刀、KISS 与 YAGNI 为指导，通过做减法降低理解和维护成本，**不是追求最少行数，也不是强行找东西删除**。

核心闭环：**建立基线 → 小步消融 → 验证交付**。

## 边界与原则

- **行为保持优先。** 保持公共 API、返回值、错误语义与可观测副作用；契约也包括非法输入的拒绝方式、权限边界、幂等性和明确的性能约束，不能只看合法输入的返回值。
- **有证据才删。** 结合实际调用路径、运行时输入来源、类型约束、配置与契约说明删减依据。测试全绿是回归证据，不是不存在其他路径的证明。拿不准就保留并说明缺什么证据，不把确认工作全部推给用户。
- **修 bug 与消融分开。** 发现已有缺陷先记录；只有用户也授权修复时，才作为独立改动处理，明确行为变化及对应回归测试。
- **范围受控。** 默认只处理用户指定范围，或上一轮新增、修改的代码及必要调用点。先查看工作区与项目约定，保留用户已有改动；不顺带重构全仓库。
- **允许零删除。** 若现有结构有实际价值，说明保留理由即可，不为了交付清单而制造改动。

与 `pre-mortem` 的区别：后者只做推演与诊断，本 skill 在获得修改授权时落地行为保持的精简。普通重构同样可以做减法；本 skill 的重点是识别并移除无价值的复杂度。

探索性 PoC、微小变更不必强行套用完整流程。用户明确要求、且有具体需求支撑的扩展点，不作为假想需求删除。

## 1. 建立基线：先立保护，再动刀

1. **确认契约与引用。** 阅读相关实现、调用点、测试和项目文档。检查导出 API、动态注册、反射、配置与外部消费者；仓库内搜不到引用，不等于无人使用。只对会改变删减决策的契约歧义询问用户。
2. **运行现有验证。** 使用项目已有测试、类型检查和 lint 命令，记录命令、范围及结果。先确认相关测试基线；已有失败需区分是否涉及目标路径，不能当成本轮引入，也不能通过删测试掩盖。
3. **补足最小保护。** 受影响行为没有可靠测试时，先补行为刻画测试（characterization tests），覆盖关键输入、输出、错误与副作用，并在原实现上跑通，再改实现。已有测试绑定私有调用时，先增加行为测试作为替代保护。
4. **区分现状与需求。** 行为刻画测试用于防止意外变化，不代表现状一定正确。可疑行为标记为待确认，不擅自把它升级为业务需求；无法确定基准时，暂停对应删减。

相关测试无法执行、或目标路径的基线失败尚未弄清时，不开始依赖该基线的大范围删减。先报告阻碍，必要时只交付建议。

## 2. 小步消融：用证据替代删减冲动

按模块或独立职责分批修改，每批运行相关测试。先改实现、用已建立的行为测试验证，再清理被替代的旧测试，避免同时改实现与预期来制造绿灯。

### 2.1 多余抽象与假想需求

- 检查接口、抽象基类、工厂、策略和适配层。**只有一个实现只是线索，不是删除依据**；它仍可能承载模块边界、依赖隔离、平台适配或稳定的外部接口。
- 若抽象不承载实际契约、替换需求或隔离价值，合并为直接表达业务语义的实现。允许引入少量直接实现替代框架代码，不把做减法理解为禁止新增任何代码。
- 删除无实际使用需求的泛化参数、配置和中间层前，确认它们不是公开配置、兼容入口或动态使用点。
- 透传包装只有在不承担公共 API、装饰器、事务、监控或生命周期职责时才内联；不为减少一层调用破坏稳定边界。

### 2.2 重复防御与死逻辑

- **可删除的重复校验**：所有入口已验证相同约束，校验后数据不会被修改或失效，下游也不存在绕过入口的调用路径。给出具体调用链与不变量，而不是只说「上游保证」。
- **类型约束不是运行时验证**：TypeScript 类型、类型断言和封闭联合不能保证网络、JSON、数据库或 JavaScript 调用方的输入合法。只有输入来源、入口验证和内部数据流共同支持时，才能据此移除兜底。
- 对 `catch`、默认值与恢复逻辑，核查被调用代码及故障来源。IO、并发、取消、资源释放和外部解析路径不能因「测试没触发」而删除；鉴权、输入校验、限流等安全边界尤其不能按冗余处理。
- 对证据不足的可疑逻辑保留原状，列出缺失信息和建议；对已经确认必要的防御直接说明保留理由，不列成待删任务。

逐项自问：**删除后，哪些契约应保持不变？依据是什么？哪项验证能发现判断错误？** 答不清就不删。

### 2.3 精简测试而不削弱保护

- 优先通过稳定的模块接口断言输入、输出、错误与可观测副作用（数据库变更、事件、状态流转），不要求所有测试都升级成端到端测试。
- 不复制实现算法生成预期值，也不只验证私有方法的调用流程；使用可独立确认的业务示例、边界值或性质断言。
- Mock 可用于隔离网络、时钟或外部服务。调用次数若表达真实契约（如扣款一次、有限次重试）可以断言；不要一概禁止交互测试。
- 删除脆弱测试前，确认其守护的行为已有替代测试，并在原实现上验证。无显式 `expect` 的测试也可能守护不抛异常、启动成功或编译通过，不能仅凭形式删除。
- 根据实际契约补边界，不机械增加并发测试。存在竞态、幂等或时序要求时，使用可控调度、屏障或假时钟，避免依赖随机等待。

## 3. 验证与交付

- 每批运行相关验证，完成后运行项目已有且适用的回归测试、类型检查、lint，以及项目要求的构建检查。根据影响范围选择验证集，明确未覆盖范围，不擅自搭建新工具链。
- 本轮引入失败时，先定位并修复；无法修复则仅撤销本轮对应改动，不覆盖用户已有工作。不要为绿灯放宽断言、跳过失败测试或改变契约。
- 工具未配置、依赖缺失或环境阻塞时，明确标注「不适用」或「未运行」及原因；无法验证的改动标为未验证，不声称完成闭环。对受阻的高影响删减停止推进。
- 检查最终 diff，确认没有混入业务修复、无关格式化、意外 API 变化或保护能力下降。

交付时说明删了什么、依据是什么、验证了什么。仓库编辑任务引用 `路径:行号` 和关键变更即可，不重复粘贴整份代码；只有用户需要代码片段时才展示实现与测试。

注释以解释 why 为主，保留必要的契约、安全约束和兼容性说明；若项目提供 `code-comments` 规范则遵循它。

## 对比示例：保持同一 API 与同一契约

以下是内部模块示例：已核查所有调用方，输入来自运行时校验过的入口，`user` 非空、等级合法、价格为有限非负数；这些校验仍保留在入口。该约束是示例前提，不能直接套用于未知项目。若函数可由外部直接调用，则需要重新确认信任边界。

### 消融前

```typescript
type UserLevel = "REGULAR" | "VIP" | "SVIP";
type User = { level: UserLevel };

interface DiscountStrategy {
  calculate(price: number): number;
}

class RateDiscountStrategy implements DiscountStrategy {
  constructor(private readonly rate: number) {}

  calculate(price: number): number {
    return price * this.rate;
  }
}

function createDiscountStrategy(level: UserLevel): DiscountStrategy {
  switch (level) {
    case "REGULAR": return new RateDiscountStrategy(1);
    case "VIP": return new RateDiscountStrategy(0.8);
    case "SVIP": return new RateDiscountStrategy(0.7);
  }
}

export function applyDiscount(user: User, price: number): number {
  return createDiscountStrategy(user.level).calculate(price);
}
```

### 消融后

```typescript
type UserLevel = "REGULAR" | "VIP" | "SVIP";
type User = { level: UserLevel };

const DISCOUNT_RATES: Record<UserLevel, number> = {
  REGULAR: 1,
  VIP: 0.8,
  SVIP: 0.7,
};

export function applyDiscount(user: User, price: number): number {
  return price * DISCOUNT_RATES[user.level];
}
```

删除依据：策略仅包装乘法和一个费率，没有额外职责；工厂只是固定映射，内部类无其他消费者。函数名、参数、返回值不变，也没有新造 `?? 1.0` 或负价归零规则。

负价格应拒绝、归零还是支持退款，取决于真实业务契约，不能由消融者自行决定。若原实现已有归零行为，也不能在消融中擅自移除。

### 原实现与精简实现共用的行为测试

以下使用项目已有的 Vitest 环境；先在消融前实现上运行，再在消融后运行，不修改预期值。

```typescript
import { expect, it } from "vitest";
import { applyDiscount } from "./discount";

it("按用户等级应用约定折扣", () => {
  expect(applyDiscount({ level: "REGULAR" }, 100)).toBe(100);
  expect(applyDiscount({ level: "VIP" }, 100)).toBe(80);
  expect(applyDiscount({ level: "SVIP" }, 100)).toBe(70);
});

it("零价格保持为零", () => {
  expect(applyDiscount({ level: "VIP" }, 0)).toBe(0);
});
```

这组测试只覆盖示例中的内部计算契约；入口对非法数据的验证测试仍需保留，不能用它替代完整回归验证。

## 输出模板

按实际情况填报，空项可省略，没有可删项时直接说明。

```markdown
## 代码消融结果

### 范围与基线
- 处理范围、已有工作区改动、契约依据。
- 基线验证命令与结果；新补的行为测试。

### 消融清单
- 删除或合并的内容 → 依据 → 相关文件位置。
- 保留的可疑项 → 缺失证据与建议。
- 发现的已有 bug → 影响与独立修复建议（本轮未修改）。

### 实现与测试
- 核心实现和行为测试的文件位置；必要时附短代码片段。

### 验证结果
- 命令 → 通过 / 失败 / 未运行 / 不适用；失败或未运行的原因。
- 遗留问题与未覆盖范围；明确是否完成验证闭环。
```
