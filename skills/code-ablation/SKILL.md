# Code Ablation & Minimalist Refactoring (代码消融与极简重构)

大模型在生成代码时存在天然的「防御性膨胀倾向」：为了显得周全或专业，容易塞入不必要的抽象层、多余的泛化、以及永远不会触发的冗余防御逻辑；而随之编写的测试也常沦为「为了覆盖率而把实现代码抄写一遍」的形式主义代码。

**代码消融（Code Ablation）** 的核心思想是**做减法**：像科学消融实验一样，系统性地移除可疑模块与过度设计，严格遵循**奥卡姆剃刀原则（如无必要，勿增实体）**与 **KISS 原则（Keep It Simple, Stupid）**——若删掉一段逻辑不影响业务正确性与契约履约，果断删掉。

本 skill 是一个包含「**消融裁剪 → 契约测试 → 交付干净代码**」的标准工程闭环。

## 它与其它操作的分工

- **vs 普通重构 (Refactoring)**：普通重构往往只调整结构甚至引入更多设计模式；代码消融的第一驱动力是**删除**与**降维**，把复杂度降到与业务需求严格匹配的最小集。
- **vs pre-mortem**：`pre-mortem` 只做推演与诊断、不改代码；`code-ablation` 则切换为严苛架构师，**直接动手剔除多余代码并交付精简实现**。
- **vs 纯修 bug**：不只修复逻辑漏洞，更重点审视是否「为了一颗螺丝钉造了一座机床」。

## 何时使用

- 刚才生成或修改了较大量代码，架构显得臃肿，存在过度设计嫌疑。
- 代码中充斥着仅有一处实现的接口/抽象基类、多余的工厂/策略模式、或大量不可能触发的空值防御与冗余转换。
- 测试用例过度依赖 Mock 内部私有方法、断言实现细节，导致一改内部实现测试就全挂（脆弱的形式主义测试）。
- 用户明确指示：「代码消融」「极简重构」「严苛自审」「做减法」「标准工程闭环」「给代码瘦身」「去过度设计」。
- **不适用场景**：
  - 探索性 PoC / 概念验证阶段（功能尚未稳定，无需过早收敛）。
  - 微小变更（如单纯修改 1 行常量或配置）。
  - 用户明确要求预留特定扩展点以应对即将到来的具体新业务。

## 3 步闭环工作流程

### 1. 代码消融（做减法 / KISS）

切换为挑剔的架构师视角，逐行审视既有实现，进行外科手术式的代码剔除：

1. **剔除过度设计与假想需求（YAGNI）**：
   - 检查所有抽象层（Interface、Abstract Class、Generic Adapter、Strategy）。如果一个接口只有一个实现类，且无跨模块解耦或单元测试隔离的硬性需求，直接拍平为具体实现。
   - 移除为「假想未来扩展」预留的参数、配置项和中间件。今天只用 SQLite，就不要手写一套通用的跨数据库 ORM 驱动层。
2. **剔除多余防御与死逻辑**：
   - 在受信任的内部调用链条上，移除重复的参数校验（例如内部私有函数重复检查上游已经验证过的非空）。
   - 移除永远不可能触发的 `catch` 分支与兜底默认值。
3. **奥卡姆剃刀原则检验**：
   - 审视每一段辅助逻辑并自问：「**如果把这段代码删掉，在所有合法的业务输入下，行为是否依然完全正确？**」只要答案为是，毫不犹豫删掉。
   - 压平无意义的调用链：若方法 A 仅仅是透传参数调用方法 B，直接内联消除方法 A。

### 2. 测试用例重构（基于业务契约，拒绝形式主义）

测试的价值在于守护业务契约，而非刷高行覆盖率指标：

1. **从业务需求与边界场景（黑盒 / 行为驱动）出发**：
   - 测试只关注公共 API 的**输入、输出与可观测副作用（数据库变更、事件发出、状态流转）**。
   - 重点补齐业务边界场景：空值、边界值、并发竞态、异常业务分支、上下游契约断言。
2. **严禁形式主义测试（Anti-patterns）**：
   - **严禁抄写实现**：若业务逻辑是 `price * discount`，严禁在测试里 Mock 乘法器或单纯验证计算流程，而应断言真实业务场景下的最终数值。
   - **严禁过度断言内部实现细节**：严禁断言某个私有方法被调用了 N 次。重构原则：**内部实现完全重写，只要对外业务契约未变，测试应 100% 保持通过**。
   - **剔除无实质断言的垃圾测试**：仅为了覆盖率跑一遍代码却无深度断言的测试直接删除。

### 3. 交付精简版最终实现

严格按两段式交付，确保减法透明、改动可审计：

1. **消融与修正简明清单**：
   - **删除的多余抽象/设计**：列出移除了哪些类、接口、泛化，并简要说明为何它是多余的。
   - **剔除的无效防御/代码**：列出移除了哪些重复校验或不可达分支。
   - **修复的业务漏洞/边界**：列出在审视契约时发现并修复的真实业务 bug。
2. **最终干净代码交付**：
   - 给出消融后的核心实现代码与重构后的契约测试代码。
   - 遵循 `code-comments` 规范：只留解释 why 的关键注释，清理废弃注释，代码本身自解释。

## 对比示例：消融前 vs 消融后

### 示例 1：业务逻辑消融

```typescript
// ❌ 消融前：过度设计（策略模式 + 工厂 + 冗余防御）
interface DiscountStrategy { calculate(price: number): number; }
class VIPDiscountStrategy implements DiscountStrategy { ... }
class DiscountStrategyFactory { ... }
function applyDiscount(user: User | null, price: number): number {
  if (!user) throw new Error("user is null"); // 上游已有前置鉴权拦截，此处永假
  const strategy = DiscountStrategyFactory.get(user.level);
  return strategy.calculate(price);
}

// ✅ 消融后：直接表达业务语义，KISS
const DISCOUNT_RATES: Record<UserLevel, number> = {
  REGULAR: 1.0,
  VIP: 0.8,
  SVIP: 0.7,
};

export function calculateDiscountPrice(level: UserLevel, price: number): number {
  const rate = DISCOUNT_RATES[level] ?? 1.0;
  return Math.max(0, price * rate);
}
```

### 示例 2：测试重构

```typescript
// ❌ 形式主义测试：把实现逻辑和内部私有调用抄一遍
it("should call discount strategy factory and calculate", () => {
  const spy = vi.spyOn(DiscountStrategyFactory, "get");
  applyDiscount(user, 100);
  expect(spy).toHaveBeenCalledWith(user.level); // 绑死了内部实现！
});

// ✅ 业务契约测试：黑盒验证真实业务行为与边界
describe("calculateDiscountPrice", () => {
  it("VIP 用户享受 8 折优惠", () => {
    expect(calculateDiscountPrice("VIP", 100)).toBe(80);
  });

  it("折扣后价格不会低于 0 元", () => {
    expect(calculateDiscountPrice("VIP", -50)).toBe(0);
  });
});
```
