# Test First：行为测试与 BDD 验收驱动

写完代码再补测试，本质是「照着自己的实现证明自己没错」：测试通过只说明代码按它已有的方式运行，不说明它做对了事。AI 尤其擅长这种循环论证——mock 所有依赖、断言内部调用次数，产出一份重构即碎、但看起来覆盖率很高的测试。

本 skill 把顺序倒过来：**验收场景 → 失败测试 → 实现 → 重构**。测试用例在实现代码之前实现并提交；测试同时是写给用户和 PM 看的验收文档，用他们能读懂的语言描述行为。

适用面：新功能开发、给已有代码补测试、评审或改造存量测试。一次性脚本、探索性 spike 不必强行套用完整流程。

## 五条原则

### 1. 测试行为，不测试实现

行为是通过稳定边界可观测的结果：公开 API 的返回值与错误、数据库与状态流转、发出的消息与副作用。实现是内部方法、调用顺序、私有状态。测试只断言前者。

自检问题：**「业务不变，只做重构（改名、抽函数、换算法、换存储），这条测试会碎吗？」** 会碎，说明它绑定了实现，多半写错了——业务没变、重构一下测试碎一地，是测试的错误，不是重构的代价。

例外：当交互本身是契约时可以断言调用——「恰好扣款一次」「告警只发一次」「重试不超过三次」。此时断言的是副作用的次数约束，不是「某个内部方法被调过」。用豁免注释标明契约依据，配置见 [references/lint-rules.md](references/lint-rules.md)。

### 2. 测试先于实现

顺序不是仪式，是防循环论证的机制：

- **先写场景能暴露需求歧义。** Given/When/Then 写不出来，说明需求没说清，先问，不要边猜边写。
- **先见红再见绿是必要证据。** 测试先按预期失败（失败原因指向「功能未实现」），才证明它真的在测东西；直接写绿的测试可能是空转测试，什么都没守护。
- **提交顺序也保持测试在前。** 同一次改动里，测试先于实现提交，任何人都能检出到测试处验证它曾经红过。

给已有代码补测试时同样从行为出发：读契约与调用方写场景，而不是读实现行数凑覆盖。

### 3. 用 BDD 写给人看的测试

标题用「业务主语 + 行为 + 条件」描述行为，主语按层选择：

- **验收层**（场景清单、e2e、API 契约测试）：以角色开头——`user is charged only once when resubmitting a paid order`。多角色系统用真实角色（admin、guest、scheduler），不一律叫 user——角色本来就是场景的关键信息。
- **单元与领域层**：以领域主语开头——`order rejects duplicate payment`、`price rounds half up`。没有用户概念的地方硬套 user，只会把领域不变量伪装成用户行为。
- **所有层的底线**：禁止实现动词和无主语命名——`calls charge once`、`test submit`、`should work`。

结构用 Given（前置状态）/ When（一个动作）/ Then（可观测结果）。词汇用业务语言：订单、扣款、库存、审批；不出现函数名、类名、私有字段、SQL——除非被测对象就是 API 契约本身。验收标准是：PM 能逐条读场景清单，并指出「这条不对」。

写实现前，先把场景清单给用户或 PM 确认。这一步比任何测试技巧都防返工，也是标题约定的执行点——标题写没写对，人在评审时判断（为什么不用 lint 管标题，见原则 5）。

### 4. 分级运行，不靠等待换信心

测试多了就分级：冒烟（关键路径，秒级，随时跑）→ 行为单测（内存级，改即跑）→ 集成（真实 DB / 网络，PR 级）→ e2e（少量，主分支与夜间）。日常用「改动文件 + 依赖图」精准选测（vitest related、jest --findRelatedTests、pytest --lf、nx affected），合并与夜间定期全量。

快靠分层和工具，不靠删测试、skip 测试。改两行代码等半天 CI，是分级没做，不是测试太多。落地配置见 [references/test-tiers.md](references/test-tiers.md)。

### 5. 规则 lint 化，但有取舍

客观有害的违规一律交给 lint 和 CI 门禁：禁 `.only` / `skip` 混入主干、禁实现耦合断言（契约性副作用豁免）、禁测试内条件分支、单测目录禁依赖真实基础设施。这些规则没有「看情况」，工具判定不会错杀；靠 review 口头维持则会随注意力衰减。

标题风格不进 lint。词表式检查会退化成「加词过检」——字符串合规不等于行为描述到位，每次违规还要人判断该不该加词，工具成了负担；它的执行点是场景评审。lint 名单保持短，每条都要答得出「这条违规为什么客观上就是伤害」。各生态配置见 [references/lint-rules.md](references/lint-rules.md)；没有 eslint 的项目用 `scripts/check-coupled-asserts.py` 兜底。

## 工作流程

1. **提炼验收场景。** 从需求列出 Given/When/Then 清单，每条标题用业务主语描述行为（验收层以角色开头，见原则 3）。写不出场景 = 需求有歧义，先澄清再动手。
2. **场景评审。** 把清单发给用户或 PM 确认；这是测试的「需求冻结」，后续实现与测试都以它为准。
3. **落成失败测试。** 逐条场景写成测试并运行，确认按预期失败、且失败信息指向功能未实现（不是测试自身写错）。先提交测试。
4. **最小实现。** 写刚好让场景变绿的实现，不预先设计场景之外的扩展点（与 code-ablation 的 YAGNI 一致）。
5. **重构。** 保持测试全绿。若重构碎了测试，把测试改回行为断言——碎的是测试，不是重构。
6. **定期全量。** 日常按分级策略跑精准测试；合并前与夜间跑全量，防止精准策略漏检。

评审存量测试时，用原则 1 的自检问题逐条过筛。实现耦合的测试重写成行为测试；删除旧断言前，确认其守护的行为已有替代断言（与 code-ablation §2.3 一致），不凭形式删除。

## 对比示例：同一行为，两种写法

场景：重复提交同一笔已创建订单，不重复扣款。

### 反例（绑定实现）

```typescript
it("calls charge once", async () => {
  const spy = vi.spyOn(paymentClient, "charge");
  await orderService.submit(order.id);
  await orderService.submit(order.id);
  expect(spy).toHaveBeenCalledTimes(1);
});
```

问题：换成「先查库判断是否已支付」的去重实现，测试立刻碎；而且它自始至终没回答「用户被扣了几次钱」——spy 通过只说明某条内部路径被走了一次。

### 正例（绑定行为）

```typescript
it("user is charged only once when the same order is resubmitted", async () => {
  // Given 一笔金额为 100 的已创建订单
  const order = await createOrder({ userId: "u1", amount: 100 });

  // When 用户重复提交同一订单
  await submitOrder(order.id);
  await submitOrder(order.id);

  // Then 该用户只被扣款一次
  expect(await chargedTotalOf("u1")).toBe(100);
});
```

`chargedTotalOf` 走测试环境的账务查询（真实或 fake 实现均可），断言的是用户可观测的结果。无论内部用去重表、状态机还是消息幂等实现，这条测试都不需要改。

## 输出模板

写测试任务按此交付；空项可省略。

```markdown
## 验收场景
- user …：Given … / When … / Then …（已确认 / 待确认）

## 测试计划
- 场景 → 测试文件 → 层级（冒烟 / 单测 / 集成 / e2e）

## 验证记录
- 红：失败输出摘要（指向功能未实现）
- 绿：通过输出摘要；运行命令与范围
- 全量：最近一次全量结果；未覆盖范围说明
```

## 与其他 skill 的分工

- `code-ablation`：给存量代码建立行为基线后做减法；本 skill 管新测试与新功能的写法与顺序。两者共用同一条测试观：测行为；契约性副作用可以断言交互次数。
- 需要 PM 直接编辑场景文本时，再升级到 Gherkin 工具链（pytest-bdd、cucumber），见 lint 参考；轻量约定足够时不上重工具。
