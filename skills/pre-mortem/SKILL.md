# Technical Pre-mortem

「事前验尸」是一个心理诡计：不问「这可能出什么错」，而是**假设它已经失败了**，站在那个失败的未来回头做尸检——「现在是失败发生后，我们在复盘：到底是什么把它带到这一步的？」

这个假设前提是本 skill 的命门，不能丢。一旦退回成「列一列风险清单」，它就和普通的 code review 没区别了，价值归零。

## 它和 code-review 的分工

先想清楚，避免做重：

- **code-review** 看「这段代码本身对不对」——bug、复用、效率，视角是**代码内部、当下**。
- **pre-mortem** 看「这个设计/代码在时间和规模的压力下会不会把人拖进事故」——视角是**系统外部、未来**。它关心 code-review 看不到的东西：演进、规模、依赖、运维、人的因素。

一句话：code-review 问「这行对不对」，pre-mortem 问「这个东西三个月后会不会变成半夜被叫起来的 oncall / 不得不回滚的发布 / 没人敢动的模块」。

**本 skill 只诊断，不改代码。** 要修复请用 code-review。保持「推演」的纯粹，让用户拿着诊断去决策。

## 何时使用

- 一个技术方案 / 架构决策 / 重构计划，在**动手前**想找出会让它失败的隐患
- 一段现有代码 / 模块，在**要不要继续依赖它、要不要大改**之前做体检
- 用户显式说「pre-mortem / 事前验尸 / 这个设计有什么坑 / 上线会不会出事 / 推演下失败场景」
- **不适用**：纯执行型、没有不确定性的任务（改个文案、加个常量）；只想找当下的 bug（那是 code-review）。

## 工作流程

### 1. 锚定 —— 先让「要验尸的东西」具体化

模糊的计划没法 pre-mortem。先确认三件事，缺了就向用户问：

- **目标**：这块东西要解决什么、服务多大的量级。
- **关键假设**：它默默依赖了哪些「现在成立、将来未必」的前提（某个外部 API 的行为、数据规模、调用方式、团队规模）。
- **即将发生的变更**：是要新写、要重构、还是要扩大依赖。

用户常常只甩一段代码、什么背景都不给。**这时不要开场就拦住用户追问 QPS/是否核心链路再开工**——代码证据本身会说话（`finally` 里只删不重连，是不是核心链路都判定得了它会掉线）。缺上下文影响的是**「可能性」分级的精度，不是能不能验尸**。所以照常基于代码证据先推，把缺的关键上下文**挂到具体某条结论上**去校准（「这条的可能性取决于真实 QPS，是 10 还是 10000？请补充我来校准」），而不是把整个分析卡在门口。

### 2. 读 —— 范围由用户的 prompt 决定

- 用户给了**目录/文件**：把它**逐行**读完。
- 用户贴了**方案/设计文档**：以文档为核心，必要时去仓库里读它将要碰的代码。
- **一跳外延**：只追核心代码*直接*调用的下游、依赖的库的用法、它的调用方入口——用来判断故障会怎么传播、边界假设是否成立。**不**无限递归整个仓库。
- 边读边记**真实证据**（文件:行号）。pre-mortem 和头脑风暴的区别就在这：每条失败推演都要挂在代码里看得见的东西上，而不是凭空想象。

### 3. 跳到失败的未来

明确设定一个时间点和一种死法，用**过去时**叙述，逼出尸检视角：

> 「现在是上线 6 个月后。这个服务上周引发了一场 P1 事故 / 这个模块已经没人敢改，新需求绕着它走 / 这次重构上线当天就回滚了。我们在复盘：发生了什么？」

### 4. 按失败原型逐一推演

用下面这张「失败原型」清单当脚手架，逐类过一遍，避免发散乱想。每一类都问：「**如果它是从这里死的，那场景长什么样？代码里有没有埋下这颗种子？**」

| 维度 | 「它已经这样失败了」长什么样 |
|---|---|
| **规模 / 性能** | 数据量涨 10 倍后崩了；N+1 查询；没分页；全量加载进内存 |
| **故障 / 韧性** | 下游一抖动它跟着雪崩；没超时 / 重试无上限 / 没降级；单点；**自反级联**——重试风暴打挂自己的 DB、缓存击穿后降级逻辑反而耗光 CPU |
| **数据正确性** | 并发写竞态；操作不幂等；迁移不可逆；缺一致性校验 |
| **可演进性** | 抽象错位，加个需求要动十个文件；硬编码；没人敢删的死代码 |
| **可运维性** | 出事了没日志 / 没指标，查不出原因；回滚不了；配置散落 |
| **依赖 / 边界** | 押注了一个会变的外部 API / 库 / 隐含假设；版本锁死或失锁 |
| **安全 / 滥用** | 接口被刷爆造成资损；越权访问（IDOR）/ 数据越界泄露；正则灾难或慢查询被用来打 DoS；逻辑漏洞被薅羊毛 |
| **静默 / 爆炸半径** | 没报错但数据悄悄写错（毒药数据，一个月后对账才发现）；非核心模块 OOM 把同进程的核心链路一起拖死 |
| **人 / 交付** | 只有一个人懂；隐含的部署顺序；测试盲区；文档与代码已脱节 |

注意区分**显性失败 vs 静默失败**：崩溃、雪崩、N+1 是显性的，会响、好发现；最致命的往往是静默的——系统照常运转，但数据已经写错、还没人收到告警。逐类推演时，对每个维度都顺手问一句「**这种死法会不会是悄无声息的？**」

只列**真正成立**的隐患——有代码证据、或方案里确实存在的假设。没证据就别硬凑，否则就掉进了 pre-mortem 自己的陷阱（为不存在的风险瞎操心）。

### 5. 追问爆炸半径与可逆性

事前验尸不只看「它怎么死」，还要看「它死的时候会拖谁陪葬、死了能不能救回来」。对每条**高严重性**的失败，再追两问：

- **爆炸半径 / 隔离性**：这个模块挂了，会不会把同进程 / 同链路的其他东西一起带走？非核心功能的故障能不能波及核心交易路径？有没有隔离边界（独立进程、超时、舱壁）挡住它。
- **可逆性 / 恢复路径**：出事后多久能恢复？特别警惕「**代码能回滚、数据回滚不了**」——一旦上线就写脏了数据 / 跑了不可逆迁移，回退代码也救不回业务状态。这种「不可逆」要单独标出来，因为它把「可回滚的发布事故」升级成「要人工修数据的长尾事故」。

### 6. 评级

给每条隐患标 **严重性 × 可能性**（高/中/低）。这一步决定了用户该先堵哪个洞——满屏风险但不排序，等于没排。缺关键上下文导致「可能性」拿不准时，按第 1 步的做法把判断依赖的那个量挂在结论上，而不是瞎拍一个数。

### 7. 收尾

- **Top 3 最该现在堵的洞**：从高严重性 × 高可能性里挑出来，每条给一句「现在能做的拦截动作」（只说做什么，不替用户改）。
- **诚实声明覆盖范围**：明说「我读了 X，没覆盖 Y」。pre-mortem 最忌讳假装看全了——范围外的地方没推演过，就不能假装推演过。这是这个方法本身的已知局限，必须守住。

## 输出格式

默认**直接在对话里输出，即用即走**（多数 pre-mortem 是决策前的快速压测，不需要存档）。只有用户明确要求时才落成 markdown 文件。

固定用这个结构：

```
## Pre-mortem：<对象> 假想失败复盘

**锚定**：目标 / 关键假设 / 即将发生的变更（各一句）

**失败原型推演**

| # | 维度 | 失败场景（过去时） | 代码证据 | 严重性 | 可能性 |
|---|------|-----|---------|--------|--------|
| 1 | 故障/韧性 | 下游超时后请求堆积，连接池耗尽，整个服务不可用 | src/client.go:42 调用无超时 | 高 | 高 |
| ... |

**Top 3 该现在堵的洞**
1. <隐患> → 现在能做的拦截动作
2. ...
3. ...

**覆盖范围**：读了 <X>；未覆盖 <Y>。
```

表格里**没有真实代码证据的行就不要写**——宁可少几行，也不要用想象凑数。
